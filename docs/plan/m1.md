# M1 执行计划 · 能聊（0.1.x）

> 对应 [ROADMAP](../../ROADMAP.md) M1 · 设计依据 [design.md](../design.md) §3（角色卡/沙箱）§4（上下文组装）§11（LLM 接入）§12（数据目录）§15（里程碑）
> 一句话目标：**装好 → 填 key → 选卡 → 聊上天，全程 ≤ 3 分钟；改卡即生效。**

## 验收标准（DoD）

1. ⬜ 干净环境实测：安装 → 首次对话 ≤ 3 分钟（代码侧已就绪：首启向导 + 安装包，需人工点验）
2. ✅ 修改 card.lua 保存后不重启即生效（热加载）——每轮从磁盘重读 + `watch.rs` 推 `card_changed`；单测 `edited_card_file_takes_effect_without_restart` 覆盖「改卡即生效」
3. ✅ SillyTavern 角色卡（PNG / JSON）导入可用——`stimport.rs` 10 例单测（含最小 PNG 往返、生成物读回校验）；真机拖放点验见下
4. ✅ 场景快照每轮注入，且在记忆检查器 v0 中可见（M1.4 起）
5. ✅ 流式输出可中断；消息编辑 / 重roll(swipe) / 删除可用（M1.5 起）
6. ✅ `pnpm build` 与 `cargo test` 双绿（66 例 Rust 单测，另 3 例真实出网测试默认忽略；`pnpm tauri build` 产出 NSIS + MSI 安装包）

## 任务分解（按依赖序）

### M1.1 配置与会话骨架 ✅

- providers.json / settings.json / personas 读取与持久化（`store.rs`）
- 会话目录与 messages.jsonl 追加式落盘
- 命令：list_providers / save_provider / list_personas
- **验收**：前端设置页可增删 provider 并持久化；会话目录按 design §12 生成
  ——数据层有单元测试覆盖（读写/追加/目录骨架/容错）；设置页 UI 已实现，
  真机点验并入 M1.9 验收清单统一执行

### M1.2 Lua 沙箱与卡片加载 ✅

- 引入 mlua。**决策点已解决：`luajit` + `vendored` 在 MSVC 下构建通过**（默认 luajit 需
  pkg-config 找系统库，Windows 不可用；vendored 源码编译即可，无需降级 lua54）
- card.lua 加载：返回 table → `Card` 静态字段 + hooks 表
- 沙箱 v0：剥离 `os/io/require`；白名单 API：`ctx.inject` / `api.memory` / `api.blackboard` / `api.ui.emit` / `api.random`（会话种子）；指令计数上限超时杀；加载或执行失败**降级为静态卡**（design §3.2）
- **验收**：示例卡 hooks（好感度）跑通；恶意卡（死循环）被杀死且不崩主程序
  ——两者均有单元测试覆盖；真机点验并入 M1.9。注意事项：LuaJIT 需 `jit.off()`
  （JIT trace 不走解释器钩子，死循环杀不死）；mlua serde 忽略字段仍遍历
  function 值，静态字段提取用白名单而非 serde 忽略未知字段

### M1.3 LLM 流式通道 ✅

- reqwest + SSE：`/chat/completions` 流式；按 `role`（chat/util）选 provider
- 命令 `send_message` → 前端流事件（delta / done / error）；中断、重试、超时
- **验收**：打字机效果流畅；断网报错可恢复；DeepSeek 与 Ollama 各实测一家
  ——SSE 解析器 7 例单测（跨块截断/CRLF/多字节 UTF-8/心跳行）；
    实际打字机效果随 M1.5 聊天 UI 验证；两家联网实测与断网恢复并入
    M1.9 验收清单（需真实 key）。实现要点：字节级按 `\n` 切行（UTF-8 安全）、
    逐块超时 180s（无整体超时，长生成不误杀）、中断保留部分文本并落盘

### M1.4 Prompt Builder v0 与黑板 v0 ✅

- A1 全局契约模板：表达契约 + 克制契约 + 资料优先级声明（design §4.1）
- A3 身份锚：scenario/personality + 命中当前情绪的示例对话
- B1 场景快照（黑板投影，每轮强制保底）+ B5 hook 注入；C3 消息窗口；全部显式标签包裹
- 黑板 v0：`day / clock / place / actors`；UI 手动编辑 + 每轮时钟步进
- **验收**：记忆检查器 v0 逐层展示本次注入内容与 token
  ——检查器在会话详情页（逐层 A1/A2/A3/B1/B5/C3、内容展开、token 估算、
    "最近一次发送"与"预览干跑"两态）；token 为启发式估算（CJK≈1:1，
    其余≈4:1，无分词器依赖），真机点验随 M1.9。A2 用户人格一并接入；
    B 槽按设计置于最新用户消息之前（独立 system 消息）；空层省略不产生空标签；
    空黑板退化为"第N天 · 地点未定"（§4.3）

### M1.5 会话与聊天 UI ✅

- 会话列表 + 新建向导 v0（选卡 + 人格 + 初始时间地点）；first_mes 开场
- IM 气泡流 + 打字机 + 停止；消息编辑 / 重roll / 删除（design §4 消息级操作）
- **验收**：完整一轮对话体验顺畅（含中文输入）

  全量重写 + 缓存失效；regenerate 先删末尾回复再流式重生成（stream_reply
  与 send_message 共用后半程）；前端聊天界面（气泡流/打字机光标/停止/

### M1.6 hooks 接入运行时 ✅

- `on_context`（B5 注入时机）与 `on_message`（消息落盘后）调用点
- `api.ui.emit` → 前端事件（表情占位显示）
- **验收**：示例卡好感度随对话变化，重启 App 后保持（state.json 持久化）
  ——实现：`card.rs` 的 `HookEnv`/`HookRun`/`UiSink` 把 hooks 变成运行时的一等公民
  （读侧快照进、三类增量出）；调用时机 `on_load` 建会话 / `on_context` 每轮组装 /
  `on_message` 消息落盘后；落盘分工 state→`state.json`、`api.memory`→`palace.jsonl`、
  `api.blackboard`→`blackboard.json`（v0 字段白名单校验）；`api.ui.emit` 实时推前端 +
  进 `done.report`。新增命令 `get_card_state`/`list_card_memory`，检查器扩成四页签
  （注入层/卡内状态/卡内记忆/事件流），会话头加表情徽标。示例卡补行为层。
  「重启后保持」的真机点验见 M1.9 清单（单测已覆盖读写往返）。
  **已知取舍（M1 记录）**：`on_message` 挂在用户消息落盘后（生成前）——重roll/编辑
  历史不会回滚 state 变化（要正确回滚需要事件日志重放，归 M2「事件流重放一致」）。

### M1.7 热加载 ✅

- notify 监听 `DataHub/characters/`，变更即重载对应卡
- **验收**：改卡保存后不重启即生效（**注**：`first_mes` 不是好探针——开场白只在建会话时
  写入 `messages.jsonl`，已有会话不会重读；用 `personality` 看署名、用 `on_context` 的注入
  文案看检查器 B5 层，二者都能在下一轮观察到）
  ——实现：解析侧本来就不缓存（每轮 `card::load_card` 从磁盘重读），热加载做的是
  「通知」：`watch.rs` 监听 characters/（递归）、personas/、settings.toml，事件去重 +
  300ms 合并后推 `card_changed`；前端 `cards.ts` 的「卡片代次」驱动卡片墙与卡内状态
  重扫。注意：不监听 `sessions/`（每轮都在写，触发刷新是噪音）。
  依赖：新增 `notify` crate（离线 registry 可得，release 构建通过）。

结论：**六项验收都不缺角色卡数据**。唯一需要准备的输入是 Ollama 本地服务（第 2 项），以及一张社区 PNG 卡——后者已用 `docs/testdata/` 的样本替代，不必外找。

**测哪种运行方式，决定你该改哪份数据**：

| 运行方式 | 数据目录 | 改卡改哪份 |
|---|---|---|
| `pnpm tauri dev` | 仓库的 `DataHub/`（cwd 向上查找命中） | 仓库 `DataHub/characters/...` |
| 便携版（exe 旁放 `DataHub/`） | exe 旁的 `DataHub/` | 那份拷贝 |
| **安装版（NSIS/MSI）** | **`%APPDATA%\huajing\DataHub`** | 那份拷贝——**在仓库改卡不会影响它** |
| 自定义 | `HUAJING_DATA` 指向的目录 | 该目录 |

安装版首次启动会把示例数据写进 `%APPDATA%\huajing\DataHub`；想让它用仓库那份，把仓库 `DataHub` 拷过去
（或设 `HUAJING_DATA`）。对照第 5 项做热加载验证时，务必改**应用实际在读的那份**卡。

样本生成方式：手写 PNG 结构（签名 + IHDR + tEXt`chara` + IEND，CRC 自算）后 base64 编码，用
`[Convert]::FromBase64String` + `[System.IO.File]::WriteAllBytes` 落盘，内容与同名 `.json` 一致。
改样本内容时记得**用二进制写入**（`[System.IO.File]::WriteAllBytes`）——按文本写会把 `0x89` 变成 `e2 80 b0`，
签名坏掉后导入器会直接报「不是 PNG 文件」。

已由单测覆盖、无需人工的部分：改卡即生效（`edited_card_file_takes_effect_without_restart`）、
钩子状态与记忆落盘并跨轮演进（`hooks_persist_state_memory_and_blackboard`）、入席建立 state 基线
（`on_load_initialises_state_from_card_defaults`）、静态卡零副作用、导入各分支与 PNG 文件端到端、
数据目录解析顺序。人工项只剩「真实 key 的联网流式体验」与「鼠标/输入法交互」。
